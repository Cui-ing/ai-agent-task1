# 第二章笔记 · 上下文工程

> 上下文 = 每次调用时模型实际"看到"的全部信息；上下文工程决定 Agent 在每个决策点能看到什么、以什么结构看到。

## 2.1 上下文：决定 Agent 能力上限的关键

- 模型在标准测试上成绩亮眼，到实际业务却常让人失望——缺的是背景信息（产品架构、业务规则、内部约定）。
- ReAct 视角：下一步行动取决于**完整交互历史**，而不是单条输入。
- 结论：模型固定时，上下文质量往往比模型规模更决定 Agent 的上限；中等模型 + 好上下文可以胜过顶级模型 + 信息匮乏。

## 2.2 Agent 如何调用大模型：API 的上下文结构

**四种消息角色**：

| 角色 | 作用 | 要点 |
|:--|:--|:--|
| system | 开发者编写的身份、权限、行为准则 | 优先级最高，通常唯一且在消息最前 |
| user | 用户输入，可含 RAG 检索引入的外部知识 | |
| assistant | 模型回复：思考过程 / 文本 / 工具调用请求 | 多轮时原样回填 |
| tool | 工具执行结果，用 `tool_call_id` 关联请求 | 下一轮思考的直接依据 |

- 工具定义走顶层 `tools` 字段：**四角色 + tools** 正好对应第一章的五个组成部分。
- **上下文 = 静态前缀（system + tools）+ 动态轨迹（user / assistant / tool）**；前缀不能动，轨迹可以压缩。
- 多轮循环：模型只负责决策（返回 `tool_calls`），框架负责执行并把结果追加回轨迹；生产系统必须设 `max_iterations` 防止死循环。

## 2.3 KV Cache 友好的上下文设计

- 原理：缓存已算好的 K/V，只计算新增 token；**token 序列从某个位置开始不同，该位置之后的缓存全部作废**——改动越靠前，代价越大。
- 反例：系统提示词里注入 `Current time: {{now}}`，每次请求前缀都变，首 token 延迟从 0.5s 涨到 3-5s，月账单近乎翻倍。
- **三条铁律**：
  1. 系统提示词与工具定义一旦确定，绝不修改（多一个空格也会失效）；
  2. 动态信息（时间戳、用户状态）永远追加到对话末尾；
  3. 使用标准 API 消息格式，不自行拼接字符串。
- Chat Template：把结构化消息翻译成线性 token 流（各家模板不同），这解释了为什么格式必须标准、前缀为什么敏感。
- KV Cache（请求内）与 Prompt Cache（跨请求前缀复用）原理相同、层级不同；缓存读取成本约为首次计算的 1/10。

## 2.4 提示工程：优化系统提示词

- 语气风格：大写 `NEVER` 比 `Please avoid` 更抓注意力，但滥用会稀释。
- 结构化：XML 语义标签（机器精确解析）+ Markdown 标题层次（人可读），互补使用。
- **流程驱动 > 规则堆砌**：给出 SOP，让模型随时知道所处阶段；上百条零散规则只会让它困惑。
- Few-shot：2-3 个覆盖边界的高质量示例，示例必须字节级稳定。
- 工具定义：写清使用边界、给出具体示例；2026 年起转向渐进式披露（完整 schema 按需加载到末尾）。
- 提示注入：外部内容伪装成系统指令劫持 Agent；上下文层防御（来源标记、指令/数据分离、输入清洗）只是第一道防线。
- **实验 2-4 的数据**：打乱信息组织 → 任务成功率降 >30%；移除工具描述 → 调用错误率 +45%。

## 2.5 动态提示词与 Agent Skills

- 动机：场景变多 → 系统提示词膨胀 → token 浪费 + 注意力稀释（上下文腐化）→ 按需加载。
- 渐进式披露三层：①元数据（name/description 常驻，description 要像路由条件）；②核心流程（选中后加载正文）；③细则与脚本（按需读取）。
- 与工具的关系：少量通用工具 + Skills，避免工具定义膨胀（第五章全书只有 7 个核心工具）。

## 2.6 Agent 状态栏

- 定义：框架在上下文末尾持续注入的结构化运行时状态（任务进度、环境变化、工具调用计数）。
- 原理：上下文学习更像**检索**而非推理，长上下文中部信息会衰减；末尾注入 = 强制注意力引导。
- **实验 2-8**：有状态栏时，小模型准确率接近前沿大模型，思考 token / 延迟 / 花费下降约一个数量级。
- 位置：作为一条 user 消息追加在末尾，不修改 system——既获得高注意力，又不破坏前缀缓存。
- 风险：模型几乎无条件相信状态栏，状态必须由代码维护，防止被污染。

## 2.7 上下文压缩策略

- 三个动机：长度/成本约束、提升思考质量、缓解"上下文焦虑"（怕窗口耗尽而提前收尾）。
- 机制：注意力擅长查找、不擅长归纳统计——**把需要思考的结论变成可直接检索的知识**。
- 长上下文会"上下文腐化"（装得下但找不到），比溢出更隐蔽，要主动显式提炼。
- **实验 2-10**：上下文感知压缩把 token 用量从 367,000 降到 40,157（减少 >75%），且保留关键信息。
- 生产五层：工具结果预算控制 → 直接删噪声 → API 层微压缩 → 归档式摘要 → 全量压缩（最后手段）。
- 隔离优于压缩：让子 Agent 承担大范围搜索等重任务，只回传几百 token 的结论。

## 实验 2-5：提示注入攻防（本机实测）

**实验设置**：`chapter2/prompt-injection`；3 种攻击（直接注入 / 间接注入 / 记忆注入）× 4 层防御（D1 无防御 → D2 提示词加固 → D3 来源标记 → D4 组合防御），每个组合重复 3 次，DeepSeek V4 Flash，temperature 0。

| 攻击 \ 防御 | D1-无防御 | D2-提示词加固 | D3-来源标记 | D4-组合防御 |
|:--|:--:|:--:|:--:|:--:|
| 直接注入 | 0% | 0% | 0% | 0% |
| 间接注入 | 0% | 0% | 0% | 0% |
| 记忆注入 | 0% | 0% | 0% | 0% |

**结论**：成功率矩阵全 0——DeepSeek V4 Flash 在 D1 无防御时就能识破全部三类注入。这与实验文档记录一致（换成强模型会抹平教学对比，原实验特意选用较弱的 gpt-4o-mini 作为"可被攻破的基线"）。全 0 不代表提示注入不危险，而是说明两点：

1. 注入攻击的成功率高度依赖模型能力，提示词加固等上下文层防御在强模型上"看不出差异"；
2. 对删除文件、发邮件等不可逆操作，仍必须保留 D4 的运行时校验——它不依赖模型自身的判断，是最后一道防线。

## 2.8 小结与收获

- 一次任务内的上下文管理：API 消息结构是骨架；稳定前缀换缓存命中；提示词 / Skills / 状态栏分别管规则 / 按需知识 / 当前状态；压缩是在保留决策、约束、失败与来源的前提下提高历史密度。
- 最大的收获：**缓存友好是前置架构约束，不是事后优化**——在系统提示词里放动态时间戳这种"小聪明"，代价会体现在延迟和账单上。
