# 第三章笔记 · 用户记忆与知识库

> 第二章管"一次任务之内"的上下文，本章扩展到"跨任务"的持久知识：用户记忆（个体、绑定用户 ID）与知识库（群体共享、领域专家）。

## 3.1 用户记忆系统

- 定位：不是保存每句对话，而是用额外的 LLM 调用**提取、压缩、审查**对未来有用的事实。
- 提取三规则：**选择性**（丢掉"搜到 3 个选项"这类过程信息）、**抽象化**（本次"靠窗"→ 长期偏好）、**结构化**（可检索的字段）。

**记忆放在哪里（层次）**：

| 层次 | 范围 | 说明 |
|:--|:--|:--|
| 轨迹 | 单次运行 | 完整历史、只增不改；运行时上下文可压缩重组 |
| 用户长期记忆 | 跨会话 | 键值对绑定用户 ID，经工具显式读写 |
| 业务状态 | 任务逻辑 | 如"等待付款"，事件驱动架构中很重要 |

轨迹是流水账，长期记忆是档案——**短期上下文 ≠ 长期记忆**：前者随任务结束消失，后者要跨会话保留并主动维护。

**记忆怎么存（格式）**：

| 格式 | 优点 | 缺点 |
|:--|:--|:--|
| Simple Notes | 最小事实、开销低 | 关联丢失 |
| Enhanced Notes | 整段叙事、语义完整 | 冗余、更新复杂 |
| JSON Cards | 可部分更新、可预测 | 分类刚性、丢多维性 |
| Advanced JSON Cards | 带 backstory/人物/时间戳，可消歧 | 生成维护成本高 |

- **实验 3-2**：Simple Notes 成本最低、能过基础回忆，但跨会话综合与消歧频繁失分；Advanced JSON Cards 在消歧与关联上最好，但维护更贵更慢。实践中按重要性混合使用。
- 可执行记忆（User as Code）：用户状态做成带类型对象、规则写成函数，借鉴"预写日志 + 检查点"。
- 认知科学三类型：情景记忆（具体事件）、语义记忆（稳定特征）、程序记忆（行为流程），与工作记忆（对应上下文窗口）正交。
- 记忆压缩三层：重要性评分筛选 → 聚类生成代表摘要 → 抽象泛化（情景升为语义/程序记忆）。
- 隐私：**实验 3-3** 日志脱敏，本地小模型做 PII 检测，召回 >95%、假阳性低于纯正则；高吞吐可用"正则 + LLM"混合。

## 3.2 RAG 基础：构建 Agent 的知识获取管道

流程：**检索相关片段 → 注入上下文 → LLM 生成**；模型训练数据有截止日期，知识库可更新。

**文档分块**：

- 必要性：嵌入长度限制 + 整篇向量主题混杂 + 只注入相关部分省窗口。
- 策略：固定大小（512 token、重叠 50-100）→ 递归/结构感知（生产默认）→ 语义切分（质量高但需额外嵌入）。
- 权衡：太小信息不全，太大主题混杂、向量稀释；起点 256-1024 token、重叠 10%-20%。
- 固有缺陷：切断与原文的上下文联系 → 由后文的"上下文感知检索"解决。

**检索方法**：

| 方法 | 原理 | 强项 | 弱项 |
|:--|:--|:--|:--|
| 稠密嵌入 | 文本→向量，语义近则向量近（余弦相似度） | 语义相似、多语言 | 精确匹配、生僻词 |
| 稀疏（BM25） | TF-IDF + 词频饱和 k1 + 长度归一化 b | 精确匹配（代码、人名） | 同义词 |
| 混合 | 并行召回 → RRF 融合 → 神经重排序 | 生产正确做法 | 复杂度 |

- **RRF**：得分 = Σ 1/(k + rank)，k 常取 60，只用排名、简单稳健。
- **重排序**：跨编码器把 query 与文档拼接做深交互，对前 N（如 50）精排；不替代融合（融合产候选池、重排精排）。
- 指标：recall@k（本书实为命中率）、MRR、nDCG，以及工业界的检索失败率。
- **实验 3-5**：从零实现 BM25——稀有词 IDF 高，贡献可超过高频词；同义词查询（cat）漏召回，暴露稀疏检索的结构性短板。

## 3.3 超越扁平文本：知识的组织与检索

- 原始案例直接入库远远不够：黑猫白猫计数、优惠资格工单等例子说明，检索到的往往是**个案**，缺少聚合结论与边界规则 → 必须在索引阶段提炼、抽象、结构化。
- **结构化索引**：
  - RAPTOR：自下而上递归聚类 + LLM 生成父摘要，支持跨抽象层检索；
  - GraphRAG：实体-关系三元组建图，强在多跳推理与实体消歧，但三元组化会语义降级。
- **知识更新**：把知识库当代码库，每次变更当 PR——Proposer 提交最小 diff，Reviewer 结合原始证据独立审核（异源模型互审），合入后增量重建索引；定期整理回到原始数据去重、合并、重建链接，冲突要写明适用场景或保留待确认。
- **智能体化 RAG（Agentic RAG）**：把检索变成 Agent 可调用的工具，用 ReAct 多轮"构造查询 → 评估是否充分 → 再检索"，从"回答问题"升级为"解决问题"。
- **上下文感知检索（Anthropic）**：索引前用 LLM 为每块生成含上下文的前缀摘要，同时增强稀疏与稠密检索；结合 BM25 检索失败率降 49%，再加重排序降 67%。
- **双层记忆架构**：少量关键事实用结构化卡片常驻（概览）+ 海量原始对话按需上下文感知检索（细节）——只常驻会丢细节，只检索缺全局视野。
- RAG 安全：检索内容是间接提示注入的典型载体；防御靠指令/数据分离 + 高风险操作独立授权。

## 实验 3-11：上下文化记忆块对用户事实召回的影响（本机实测）

**实验设置**：`chapter3/contextual-retrieval-for-user-memory`，离线 BM25 代理，12 个记忆块、8 个查询。

| 方法 | Recall@1 | Recall@3 | MRR |
|:--|:--:|:--:|:--:|
| Plain（直接索引原始块） | 0.625 | 1.000 | 0.792 |
| Contextual（上下文化后索引） | 0.750 | 1.000 | 0.875 |
| 提升（Δ） | +0.125 | +0.000 | +0.083 |

**结论**：孤立片段（如"好的，就订这个吧"）在 Plain 下缺乏可检索信号；加上上下文前缀后被"锚定"回情境，召回名次明显提升（如"西雅图酒店是哪家"从第 3 名升到第 1 名）。

## 实验 3-8：智能体化 RAG vs 非智能体化（本机实测）

**实验设置**：`chapter3/agentic-rag`，内置离线 BM25 法律语料（288 篇、21372 个分块），DeepSeek V4 Flash，`--mode compare`，查询"醉酒过失致人重伤且有盗窃前科如何量刑"。

- **非智能体化（单次检索）**：只确认了过失致人重伤的基础法定刑，对"醉酒影响""盗窃前科是否构成累犯"回答"知识库中不包含相关规定，无法据此回答"。
- **智能体化（多轮迭代检索，10 轮内 4 次检索）**：第 1 轮并行检索三个子问题 → 第 2-3 轮发现缺"累犯认定" → 补充检索《刑法》第 65 条，得出关键结论：**后罪为过失犯罪，依法不构成累犯，不能适用累犯从重处罚**；并给出完整量刑分析表。

**结论**：简单问题上两种模式差别不大；复杂问题（多跳、需要拆解）上，智能体化 RAG 通过自主构造查询、评估信息充分性再检索，显著提升答案质量，代价是响应时间与检索次数增加。

## 实验扩展：检索参数对比（top-k 2 vs 5）

**实验设置**：`compare_offline.py --top-k 2` 与 `--top-k 5`，对比单次检索与分解式多轮检索的证据召回率。

| 检索深度 | 单次检索（全部/复杂题） | 分解检索（全部/复杂题） | 检索次数 |
|:--|:--:|:--:|:--:|
| top-k=2 | 48% / 33% | 81% / 92% | 1.0 → 1.3 |
| top-k=5 | 76% / 58% | 100% / 100% | 1.0 → 1.3 |

**结论**：检索深度不足（top-k=2）会明显拉低召回，但分解式多轮检索能部分补偿（复杂题 33% → 92%）；加大 top-k 到 5 后，智能体化检索把证据召回率补到 100%。说明**检索深度与检索轮数之间存在权衡**，而不是单靠调大 top-k。

## 3.4 小结与收获

- 持久知识分两个尺度：个人用户记忆（读取 → 后台提取候选 → 来源与策略核验 → 更新）与共享知识库；知识库主流水线是"分块 → 稠密/稀疏检索 → 融合 → 重排序 → 生成"，用 recall@k 等指标验收。
- 区分短期上下文与长期记忆：轨迹/工作记忆负责"这次任务"，用户记忆与知识库负责"跨任务"；两者用同一套检索与压缩技术，但生命周期、更新方式、隐私要求不同。
- RAG 在 Agent 中的角色：不是"给模型塞资料"这么简单，而是把知识变成**可检索、可验证、可更新**的工具；智能体化 RAG 进一步把检索的控制权交给模型。
- 最大的收获：**索引质量决定检索上限**——分块策略、上下文前缀、结构化概览这些"索引期"的工作，比在检索时调参更有效。
